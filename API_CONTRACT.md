# GEEKA API Contract

**API version:** v1
**Base URL (local):** `http://127.0.0.1:8000`
**Purpose:** Shared agreement between the Django backend and React frontend.

## 1. Customer Authentication

### 1.1 Register

Creates a customer account and sends an email verification code.

* **Method:** `POST`
* **Endpoint:** `/api/v1/auth/register/`
* **Authentication:** Not required
* **Content-Type:** `application/json`

**Request body**

```json
{
  "email": "customer@example.com",
  "full_name": "Aarav Sharma",
  "password": "ExamplePass123!",
  "password_confirm": "ExamplePass123!"
}
```

| Field              | Type   | Required | Validation                                  |
| ------------------ | ------ | -------- | ------------------------------------------- |
| `email`            | string | Yes      | Valid email; must not already be registered |
| `full_name`        | string | Yes      | Maximum 150 characters                      |
| `password`         | string | Yes      | Minimum 8 characters                        |
| `password_confirm` | string | Yes      | Must match `password`                       |

**Success response — `201 Created`**

```json
{
  "message": "Registration successful. Verification code sent to your email.",
  "user": {
    "id": "user-uuid",
    "email": "customer@example.com",
    "full_name": "Aarav Sharma",
    "email_verified": false
  }
}
```

The `id` is a UUID generated by the backend. The example value above is illustrative.

**Validation error response — `400 Bad Request`**

```json
{
  "errors": {
    "email": [
      "An account with this email already exists."
    ]
  }
}
```

The `errors` object may contain field-specific messages for invalid email, missing or invalid fields, password length, or password confirmation mismatch. The frontend should display the message associated with each field when available.

**Expected behavior**

1. The backend validates the submitted data.
2. It creates the account with `email_verified` set to `false`.
3. It generates a verification code, stores its hash, and sends the code to the submitted email.
4. The frontend shows a message asking the customer to check their email and continue to verification.

**Important**

* The frontend must not generate or decide the verification code.
* Do not store or send the customer's password back in the response.
* The account is not yet email-verified after registration.
* This contract documents the current registration endpoint. If implementation behavior or response fields change, update this section to match.


### 1.2 Verify Email

Verifies the customer's email using the OTP sent during registration.

- **Method:** `POST`
- **Endpoint:** `/api/v1/auth/verify-email/`
- **Authentication:** Not required
- **Content-Type:** `application/json`

**Request body**

```json
{
  "email": "aditya.test.geeka@gmail.com",
  "otp": "123456"
}
```

**Success response — `200 OK`**
```json
{
  "message": "Email verified successfully.",
  "user": {
    "id": "user-uuid",
    "email": "aditya.test.geeka@gmail.com",
    "full_name": "Aditya Gupta",
    "email_verified": true
  }
}
```

**Error response — `400 Bad Request`**
```json
{
  "error": "Invalid verification code."
}
```
Other possible errors include an expired OTP, no active verification code, or maximum verification attempts exceeded.

## 1.7 Password Reset Request

Requests a password reset code for a customer account.

### Request

- **Method:** `POST`
- **Endpoint:** `/api/v1/auth/password-reset/request/`
- **Authentication:** Not required
- **CSRF:** Required
- **Content-Type:** `application/json`

### Request Body

```json
{
  "email": "customer@example.com"
}
```

### Success Response — `200 OK`

The same response is returned whether or not an account exists with the provided email. This prevents account/email enumeration.

```json
{
  "message": "If an account exists with this email, a password reset code has been sent."
}
```

### Validation Error — `400 Bad Request`

```json
{
  "errors": {
    "email": [
      "Enter a valid email address."
    ]
  }
}
```

### Behavior

1. Normalize the provided email address.
2. Check whether an active account exists.
3. If the account exists, invalidate any previous unused password reset code.
4. Generate a new 6-digit password reset code.
5. Store only the hashed code.
6. Set the code expiry to 10 minutes.
7. Send the code to the registered email through Brevo.
8. Return the same generic success message regardless of account existence.

## 1.8 Password Reset OTP Verification

Verifies that the password reset code is valid before allowing the customer to reset their password.

### Request

- **Method:** `POST`
- **Endpoint:** `/api/v1/auth/password-reset/verify/`
- **Authentication:** Not required
- **CSRF:** Required
- **Content-Type:** `application/json`

### Request Body

```json
{
  "email": "customer@example.com",
  "otp": "123456"
}
```

### Success Response — `200 OK`

```json
{
  "message": "Verification code is valid."
}
```

### Invalid or Expired Code — `400 Bad Request`

```json
{
  "error": "Invalid verification code."
}
```

or:

```json
{
  "error": "Password reset code has expired."
}
```

### Attempt Limit

A maximum of 5 verification attempts is allowed for a password reset code.

After the maximum number of attempts is reached:

```json
{
  "error": "Maximum verification attempts exceeded."
}
```

### Behavior

1. Find the latest unused password reset code for the provided account.
2. Check whether the code has expired.
3. Check whether the maximum number of attempts has been reached.
4. Increment the attempt counter.
5. Compare the submitted OTP with the stored hash.
6. Return success if the OTP is valid.
7. The OTP remains available for the password reset confirmation step until it is used or expires.

---

## 1.9 Password Reset Confirmation

Sets a new password after validating the password reset code.

### Request

- **Method:** `POST`
- **Endpoint:** `/api/v1/auth/password-reset/confirm/`
- **Authentication:** Not required
- **CSRF:** Required
- **Content-Type:** `application/json`

### Request Body

```json
{
  "email": "customer@example.com",
  "otp": "123456",
  "password": "NewPassword123!",
  "password_confirm": "NewPassword123!"
}
```

### Success Response — `200 OK`

```json
{
  "message": "Password reset successful. Please log in with your new password."
}
```

### Validation Error — `400 Bad Request`

```json
{
  "errors": {
    "password_confirm": [
      "Passwords do not match."
    ]
  }
}
```

### Invalid or Expired Code — `400 Bad Request`

```json
{
  "error": "Invalid verification code."
}
```

or:

```json
{
  "error": "Password reset code has expired."
}
```

### Behavior

1. Validate the request data.
2. Find the latest unused password reset code for the account.
3. Validate the OTP, expiry, and attempt limit.
4. Hash and store the new password using Django's password hashing system.
5. Mark the password reset code as used.
6. Prevent the same OTP from being reused.
7. Return a successful password reset response.

### Security Requirements

- Passwords must never be stored in plaintext.
- Password reset codes must never be stored in plaintext.
- Password reset codes expire after 10 minutes.
- A maximum of 5 OTP attempts is allowed.
- Requesting a new reset code invalidates the previous unused code.
- A successfully used reset code cannot be reused.
- Password reset must not reveal whether an email address is registered.


## 1.10 Google Login

### Endpoint

`GET /api/v1/auth/google/login/`

### Purpose

Starts the Google OAuth 2.0 authentication flow for GEEKA users.

### Authentication

- Authentication required: No
- CSRF required: No
- OAuth state validation: Yes
- PKCE: Yes

### Request

No request body or query parameters are required.

The frontend must redirect the browser to this endpoint.

```text
http://127.0.0.1:8000/api/v1/auth/google/login/
```

Example frontend implementation:

```javascript
window.location.href =
    "http://127.0.0.1:8000/api/v1/auth/google/login/";
```

### Response

This endpoint does not return a JSON response.

It returns:

```text
HTTP 302 Found
```

The browser is redirected to Google's OAuth authorization page.

After successful authentication, Google redirects the browser to:

`GET /api/v1/auth/google/callback/`

### Security

- OAuth state is generated by the backend and stored in the Django session.
- PKCE code verifier is generated and stored in the Django session.
- The frontend does not handle or store Google OAuth tokens.
- No JWT is stored in `localStorage` or `sessionStorage`.
- Authentication is established using the Django server-side session.

---

## 1.11 Google OAuth Callback

### Endpoint

`GET /api/v1/auth/google/callback/`

### Purpose

Handles the OAuth callback from Google, verifies the Google account, creates or retrieves the corresponding GEEKA user, establishes the Django authenticated session, and redirects the user to the frontend.

### Authentication

- Authentication required: No
- CSRF required: No
- OAuth state validation: Yes
- PKCE verification: Yes

### Query Parameters

| Parameter | Required | Description |
|---|---|---|
| `code` | Yes | Authorization code returned by Google |
| `state` | Yes | OAuth state generated by GEEKA |
| `error` | No | Error returned by Google if authorization fails |

### Request Body

None.

### Successful Response

The backend establishes the Django authenticated session and returns:

```text
HTTP 302 Found
```

The browser is redirected to the frontend:

```text
http://localhost:5173/
```

### User Handling

If the Google email does not already exist in GEEKA:

- A new GEEKA user is created.
- The Google email is stored as the user's email.
- The Google-provided name is stored as `full_name`.
- `email_verified` is set to `true`.
- The user is created with an unusable local password.

If the Google email already belongs to an existing GEEKA user:

- The existing user account is used.
- The existing password is not changed.
- The account's `email_verified` value is set to `true` if required.

### Authentication Session

After successful Google authentication, the user is logged into GEEKA using the Django server-side session.

The frontend can verify the authenticated session using:

`GET /api/v1/auth/me/`

### Error Handling

If OAuth state validation fails:

```text
HTTP 400/403
```

If the authorization code is missing or invalid:

```text
HTTP 400
```

If Google authentication fails:

```text
HTTP 400
```

The backend must not create or authenticate a user unless the Google identity has been successfully verified.

### Important Frontend Note

The frontend must not call the callback endpoint using `fetch()`.

The Google authentication flow must be initiated by redirecting the browser to:

`GET /api/v1/auth/google/login/`

The browser handles the Google authentication and callback redirects automatically.

# 2. Product Catalog

This section documents the APIs used for managing product catalog data.

Catalog APIs are divided into:

* Public catalog APIs for customers and storefront browsing.
* Admin catalog APIs for staff users managing products and product images.

All catalog endpoints use the `/api/v1/catalog/` base path.

---

## 2.1 Admin Product Image Upload

Uploads an image for an existing product.

The uploaded image is stored in the private Supabase Storage `product-images` bucket. The database stores only the stable storage path/reference. The API returns a temporary signed URL that the frontend can use to display the uploaded image.

### Endpoint

`POST /api/v1/catalog/admin/products/<product_id>/images/`

### Authentication

* Authentication required: Yes
* Authentication method: Django server-side session
* Permission required: Staff/Admin user
* CSRF required: Yes

Only authenticated Django staff users can upload product images.

Normal customers must not be allowed to access this endpoint.

### Content-Type

`multipart/form-data`

### Path Parameters

| Parameter    | Required | Type | Description                                    |
| ------------ | -------- | ---- | ---------------------------------------------- |
| `product_id` | Yes      | UUID | UUID of the product to which the image belongs |

### Request Body

| Field           | Type    | Required | Description                                                       |
| --------------- | ------- | -------- | ----------------------------------------------------------------- |
| `image_file`    | File    | Yes      | Product image file                                                |
| `display_order` | Integer | No       | Position of the image in the product image gallery. Default: `0`  |
| `is_primary`    | Boolean | No       | Whether this image is the primary product image. Default: `false` |

### Image Validation

The backend validates every uploaded product image before storing it.

The following rules apply:

* Maximum file size: `400 KB`
* Maximum dimensions: `2000 × 2000` pixels
* Allowed formats:

  * JPG
  * JPEG
  * PNG
  * WebP
* The uploaded file must be a valid image.
* Corrupted or invalid image files are rejected.
* The backend generates the final storage filename.
* The original filename is not used as the storage filename.

### Storage

Product images are stored in the private Supabase Storage bucket:

`product-images`

The storage path follows this structure:

```text
products/<product_id>/<generated_filename>
```

Example:

```text
products/46cb81d6-dc2d-4534-9847-44e14614466f/a58af335c9cd4a5f96d654f22621742f.webp
```

The database stores this storage path in the `ProductImage.image` field.

The database must not store the actual image file.

The database must not store a permanent public URL.

Because the bucket is private, the frontend receives a temporary signed URL when an image is returned by an API.

### Successful Response — `201 Created`

```json
{
  "id": "product-image-uuid",
  "product_id": "product-uuid",
  "image_url": "temporary-signed-url",
  "display_order": 0,
  "is_primary": true,
  "is_active": true
}
```

### Response Fields

| Field           | Type    | Description                                   |
| --------------- | ------- | --------------------------------------------- |
| `id`            | UUID    | Unique ID of the product image                |
| `product_id`    | UUID    | ID of the associated product                  |
| `image_url`     | String  | Temporary signed URL generated by the backend |
| `display_order` | Integer | Display position of the image                 |
| `is_primary`    | Boolean | Whether this is the primary image             |
| `is_active`     | Boolean | Whether the image is active                   |

### Validation Error — `400 Bad Request`

If the uploaded image fails validation, the API returns a validation error.

Example:

```json
{
  "image_file": [
    "Image size must be 400 KB or less."
  ]
}
```

Other validation errors may occur for:

* Unsupported image format
* Invalid or corrupted image
* Image dimensions greater than `2000 × 2000`
* Invalid request fields

### Authentication Error — `401 Unauthorized`

Returned when the request does not contain an authenticated Django session.

```json
{
  "detail": "Authentication credentials were not provided."
}
```

### Permission Error — `403 Forbidden`

Returned when the user is authenticated but is not a staff/admin user.

```json
{
  "detail": "You do not have permission to perform this action."
}
```

### Product Not Found — `404 Not Found`

Returned when the supplied `product_id` does not belong to an existing product.

```json
{
  "detail": "Not found."
}
```

### Image Upload Behavior

The backend performs the following operations:

1. Validate the uploaded image.
2. Generate a safe server-side filename.
3. Upload the image to the private Supabase Storage bucket.
4. Create the corresponding `ProductImage` database record.
5. Generate a temporary signed URL.
6. Return the image information to the frontend.

If database creation fails after the image has already been uploaded to Supabase Storage, the backend removes the uploaded storage object to prevent orphaned files.

### Important Frontend Notes

The frontend must:

* Send the image using `multipart/form-data`.
* Send the product UUID in the URL.
* Include the authenticated Django session.
* Include the CSRF token for the state-changing request.
* Treat `image_url` as a temporary signed URL.
* Not assume that the stored database value of `ProductImage.image` is a browser-ready URL.
* Not upload directly to the Supabase Storage bucket through this API flow.
* Not generate product image filenames itself.

### Product Image Rules

Product images are currently associated with the product itself rather than individual variants.

Each product may contain multiple images.

The image gallery uses `display_order` to determine image ordering.

Only one image can be marked as the primary image for a product.

Inactive product images are not intended to be displayed in the public storefront.

---

## 2.2 Product Image Data Model

The product image API corresponds to the following product image data:

| Field           | Type               | Description                     |
| --------------- | ------------------ | ------------------------------- |
| `id`            | UUID               | Primary key                     |
| `product`       | UUID / Foreign Key | Associated product              |
| `image`         | String             | Supabase Storage path/reference |
| `display_order` | Integer            | Image display position          |
| `is_primary`    | Boolean            | Primary image flag              |
| `is_active`     | Boolean            | Image visibility/active state   |
| `created_at`    | DateTime           | Creation timestamp              |
| `updated_at`    | DateTime           | Last update timestamp           |

The `image` field stores the Supabase Storage path rather than the actual image file or a permanent public URL.

---

## 2.3 Product Image Storage and URL Handling

Product images use private Supabase Storage.

The backend is responsible for generating temporary signed URLs when an image needs to be returned to the frontend.

Example storage reference:

```text
products/<product_id>/<generated_filename>
```

Example API image URL:

```text
https://<supabase-project>.supabase.co/storage/v1/object/sign/product-images/...
```

The exact signed URL is generated dynamically and may change whenever a new signed URL is generated.

The frontend must therefore use the `image_url` returned by the API and must not construct Supabase Storage URLs manually.

The frontend must also not treat the storage path stored in the database as a public image URL.

---

## 2.4 Admin Product Image Upload — Frontend Flow

The expected frontend flow is:

1. Staff/admin logs into GEEKA through the normal login page.
2. The authenticated Django session is established.
3. The frontend verifies the authenticated user using:

`GET /api/v1/auth/me/`

4. If the user has staff/admin permissions, the frontend may display the admin Dashboard option.
5. The admin opens the product management interface.
6. The admin selects a product.
7. The admin selects an image file.
8. The frontend sends the image to:

`POST /api/v1/catalog/admin/products/<product_id>/images/`

9. The backend validates and uploads the image.
10. The backend returns the product image data and temporary signed URL.
11. The frontend uses `image_url` to display the uploaded image.

The backend remains the final authority for authentication, authorization, validation, storage, and product image state.

---

## 2.5 Admin Product Image Security Requirements

* Product image upload requires an authenticated Django session.
* Only staff/admin users may upload product images.
* CSRF protection must remain enabled for the state-changing request.
* Image files must be validated by the backend.
* File size limits must be enforced by the backend.
* Image format validation must be enforced by the backend.
* Image dimensions must be validated by the backend.
* Supabase Storage credentials must never be exposed to the frontend.
* The Supabase service/secret key must never be returned through an API response.
* Product image storage paths must not expose Supabase credentials.
* The frontend must not directly access private Supabase Storage using backend secret credentials.
* Signed URLs must be generated by the backend.
* The backend must remain the source of truth for product image permissions and state.

## 2.6 Admin Product Image Upload

Uploads an image for an existing product.

* **Method:** `POST`
* **Endpoint:** `/api/v1/catalog/admin/products/<product_id>/images/`
* **Authentication:** Required
* **Permission:** Staff/Admin only
* **CSRF:** Required
* **Content-Type:** `multipart/form-data`

### Path Parameter

| Parameter    | Type | Required | Description                                  |
| ------------ | ---- | -------- | -------------------------------------------- |
| `product_id` | UUID | Yes      | ID of the product to which the image belongs |

### Request Body

| Field           | Type    | Required | Default | Description                                             |
| --------------- | ------- | -------- | ------- | ------------------------------------------------------- |
| `image_file`    | File    | Yes      | —       | Product image                                           |
| `display_order` | integer | No       | `0`     | Position of the image in the product gallery            |
| `is_primary`    | boolean | No       | `false` | Whether the image should be the product's primary image |

### Image Requirements

* Maximum file size: **400 KB**
* Maximum dimensions: **2000 × 2000 pixels**
* Allowed formats: **JPG, JPEG, PNG, WebP**
* The uploaded file must be a valid image.
* A product can have a maximum of **5 images**.

### Success Response — `201 Created`

```json
{
  "id": "product-image-uuid",
  "product_id": "product-uuid",
  "image_url": "temporary-signed-url",
  "display_order": 0,
  "is_primary": false,
  "is_active": true
}
```

The `image_url` is a temporary signed URL generated by the backend for accessing the private product image.

### Primary Image Behavior

A product can have only one primary image.

If `is_primary` is submitted as `true`:

1. The newly uploaded image becomes the primary image.
2. Any existing primary image for the same product is automatically changed to `is_primary=false`.
3. The API returns the newly uploaded image with `is_primary=true`.

If `is_primary` is `false`, the image is added as a normal gallery image.

### Maximum Image Limit

A product can have a maximum of **5 images**.

If the product already contains 5 images, another upload is rejected.

**Response — `400 Bad Request`**

```json
{
  "detail": "A product can have a maximum of 5 images."
}
```

### Validation Errors — `400 Bad Request`

Invalid or unsupported images are rejected with an appropriate validation error.

Possible validation failures include:

* Image exceeds 400 KB.
* Image dimensions exceed 2000 × 2000 pixels.
* Unsupported image format.
* Invalid or corrupted image file.
* Product already contains 5 images.

### Authentication and Permission Errors

**Unauthenticated — `401 Unauthorized`**

The endpoint requires an authenticated Django session.

**Unauthorized — `403 Forbidden`**

The authenticated user does not have staff/admin permissions.

### Not Found — `404 Not Found`

Returned when the specified `product_id` does not correspond to an existing product.

### Frontend Notes

* The frontend must send the request using `multipart/form-data`.
* The frontend must not generate storage filenames.
* The frontend must not construct permanent image URLs.
* The `image_url` returned by the backend can be used to display the uploaded image.
* When uploading a new primary image, the frontend does not need to separately unset the previous primary image.
* The backend is responsible for maintaining the single-primary-image rule.
* The frontend should prevent unnecessary uploads after the product already has 5 images when the current image count is known.

---

## 2.7 Product Image Response

Product image data returned by catalog APIs uses the following structure:

```json
{
  "id": "product-image-uuid",
  "image_url": "temporary-signed-url",
  "display_order": 0,
  "is_primary": true,
  "is_active": true
}
```

### Image Ordering

Images are ordered using `display_order`.

The frontend should use the returned `display_order` value when rendering the product image gallery.

### Primary Image

The image with:

```json
"is_primary": true
```

should be treated as the product's main/cover image.

A product can have at most one primary image.

### Active Images

Only images with:

```json
"is_active": true
```

should be displayed in the public product catalog.

---

## 2.8 Product Image API Rules

* Product images belong to the product, not to individual variants.
* Product image IDs are UUIDs.
* Product image URLs are temporary signed URLs because product images are stored privately.
* The frontend must treat `image_url` as a browser-ready temporary URL and must not assume it is permanent.
* The backend remains the source of truth for image ordering, primary-image selection, image limits, and image visibility.
* Product image upload is restricted to staff/admin users.


## 2.9 Public Product List

Returns products that are publicly visible in the GEEKA storefront.

### Request

* **Method:** `GET`
* **Endpoint:** `/api/v1/catalog/products/`
* **Authentication:** Not required
* **CSRF:** Not required
* **Content-Type:** Not applicable

### Visibility Rules

Only products with:

```text
status = PUBLISHED
```

are returned.

Products with the following statuses are not returned:

* `DRAFT`
* `ARCHIVED`

The backend is the source of truth for product visibility.

### Success Response — `200 OK`

```json
[
  {
    "id": "product-uuid",
    "name": "Handmade Crochet Bag",
    "slug": "handmade-crochet-bag",
    "category": {
      "id": 1,
      "name": "Handmade",
      "slug": "handmade"
    },
    "primary_image": {
      "id": "product-image-uuid",
      "image_url": "temporary-signed-url",
      "display_order": 0,
      "is_primary": true
    }
  }
]
```

### Response Fields

| Field                         | Type        | Description                                      |
| ----------------------------- | ----------- | ------------------------------------------------ |
| `id`                          | UUID        | Stable unique ID of the product                  |
| `name`                        | string      | Product name                                     |
| `slug`                        | string      | Unique product slug                              |
| `category`                    | object      | Category information associated with the product |
| `category.id`                 | integer     | Category ID                                      |
| `category.name`               | string      | Category name                                    |
| `category.slug`               | string      | Category slug                                    |
| `primary_image`               | object/null | Primary active product image                     |
| `primary_image.id`            | UUID        | Product image ID                                 |
| `primary_image.image_url`     | string      | Temporary signed URL for the private image       |
| `primary_image.display_order` | integer     | Image display order                              |
| `primary_image.is_primary`    | boolean     | Indicates the primary image                      |

### Primary Image Behavior

The `primary_image` field contains the product's active primary image.

If the product does not have an active primary image:

```json
"primary_image": null
```

The frontend must handle `null` and must not assume that every product has an image.

### Image URL Behavior

The `image_url` is a temporary signed URL generated by the backend.

The frontend may use the URL directly to display the image.

The frontend must not:

* construct Supabase Storage URLs
* construct storage paths
* assume the URL is permanent
* store the URL as a permanent product reference

The product image UUID and product UUID are the stable identifiers.

### Product Ordering

Products are returned in newest-first order using the product creation timestamp.

The backend controls the ordering.

### Stock Behavior

The product list does not hide a published product merely because it is out of stock.

A published product may therefore appear in the storefront even when all of its active variants have zero stock.

Stock and purchasability information is provided by the product detail endpoint.

### Empty Result

If no published products are available:

```json
[]
```

### Authentication

No authentication is required.

This endpoint is publicly accessible to storefront visitors, including guest users.

### Frontend Notes

The frontend should:

* render the returned products directly from the API response
* use `id` as the stable product identifier
* use `slug` for display/navigation where appropriate
* use `primary_image.image_url` for the product card image
* handle `primary_image: null`
* not create fake/default product values
* not determine whether a product is published
* not determine product stock status from the product list

### Product Images

Only active product images should be returned.

Images are ordered using:

```text
display_order
```

The frontend should preserve the returned order when displaying the product gallery.

The image with:

```json
"is_primary": true
```

is the product's primary/cover image.

### Product Variants

Only active variants are returned.

Each variant contains its complete attribute combination.

The frontend must use the returned variant data to allow the customer to select the appropriate product configuration.

The frontend must not hardcode product attributes such as:

* Size
* Color
* Material

The available attributes and values are controlled by the backend.

### Stock and Purchasability

`stock` is controlled by the backend.

The frontend must not calculate or modify stock.

`in_stock` is:

```text
true
```

when the variant is active and has stock greater than zero.

`is_low_stock` is controlled by the variant's backend low-stock threshold.

A threshold of `0` means low-stock warnings are disabled.

`is_purchasable` is:

```text
true
```

when at least one active variant has stock greater than zero.

A published product can therefore be visible while:

```json
"is_purchasable": false
```

when all active variants are out of stock.

### Out-of-Stock Products

Out-of-stock products are not automatically changed to `DRAFT`.

A published product remains publicly visible even when it has no available stock.

The frontend may use:

```text
is_purchasable
```

and each variant's:

```text
in_stock
```

to determine the appropriate storefront state.

### Image URL Behavior

Product images are stored in private Supabase Storage.

The backend returns temporary signed URLs through:

```text
image_url
```

The frontend must treat these URLs as temporary browser-ready URLs.

The frontend must not construct or modify Supabase Storage URLs.

### Not Found — `404 Not Found`

If the specified product does not exist or is not publicly visible:

```text
HTTP 404 Not Found
```

The frontend should treat the product as unavailable rather than attempting to display a draft or archived product.

### Authentication

No authentication is required.

This endpoint is publicly accessible to storefront visitors, including guest users.

### Frontend Notes

The frontend should:

* use the product UUID as the stable product identifier
* fetch the product using the product ID
* render only the data returned by the backend
* handle empty image arrays
* handle products with multiple variants
* handle products that are currently out of stock
* use backend-provided stock and purchasability information
* not generate fake/default product data
* not hardcode v


## 2.11 Public Product List

### Endpoint

`GET /api/v1/catalog/products/`

### Authentication

* Public endpoint.
* No authentication required.
* No CSRF token required.

### Purpose

Returns the storefront product catalog using server-side pagination.

Only products with:

```text
status = PUBLISHED
```

are included.

Product visibility is independent of category activity status. A published product remains visible even if its associated category is inactive.

### Query Parameters

#### `page`

Optional page number.

Example:

`GET /api/v1/catalog/products/?page=2`

* Page numbering starts at `1`.
* Backend page size is fixed at **20 products per page**.
* Frontend must use the `next` and `previous` URLs returned by the API rather than calculating pagination URLs itself.

#### `category`

Optional category slug used to filter products.

Example:

`GET /api/v1/catalog/products/?category=handmade`

Rules:

* Category filtering uses the category `slug`.
* Only active categories can be used for public category filtering.
* If the requested category is inactive or does not exist, the filtered result is empty.
* Category filtering can be combined with pagination.

Example:

`GET /api/v1/catalog/products/?category=handmade&page=2`

### Response

The endpoint returns a paginated response:

```json
{
    "count": 47,
    "next": "http://127.0.0.1:8000/api/v1/catalog/products/?page=2",
    "previous": null,
    "results": [
        {
            "id": "46cb81d6-dc2d-4534-9847-44e14614466f",
            "name": "Handmade Crochet Bag",
            "slug": "handmade-crochet-bag",
            "category": {
                "id": 1,
                "name": "Handmade",
                "slug": "handmade"
            },
            "primary_image": {
                "id": "c21844a0-9faf-4bb9-92ba-5f7fdcd92bca",
                "image_url": "SIGNED_URL",
                "display_order": 0,
                "is_primary": true
            }
        }
    ]
}
```

### Response Fields

#### `count`

Total number of products matching the current filters.

#### `next`

URL for the next page.

Returns `null` when there is no next page.

#### `previous`

URL for the previous page.

Returns `null` when there is no previous page.

#### `results`

Array containing the products for the current page.

Each product contains:

| Field                         | Type        | Description                                   |
| ----------------------------- | ----------- | --------------------------------------------- |
| `id`                          | UUID        | Stable product ID                             |
| `name`                        | string      | Product name                                  |
| `slug`                        | string      | Product slug                                  |
| `category`                    | object      | Product category information                  |
| `category.id`                 | integer     | Category ID                                   |
| `category.name`               | string      | Category name                                 |
| `category.slug`               | string      | Category slug                                 |
| `primary_image`               | object/null | Product's active primary image                |
| `primary_image.id`            | UUID        | Image ID                                      |
| `primary_image.image_url`     | string      | Temporary signed Supabase Storage URL         |
| `primary_image.display_order` | integer     | Image display order                           |
| `primary_image.is_primary`    | boolean     | Always `true` when `primary_image` is present |

### Primary Image Rules

* Only active images can be returned.
* Only the product's primary image is returned.
* If no active primary image exists, `primary_image` is `null`.
* Image URLs are temporary signed URLs because the Supabase Storage bucket is private.
* Frontend must not construct Supabase Storage URLs manually.
* Frontend should use the returned `image_url` directly.

### Ordering

Products are returned newest first:

```text
created_at DESC
```

### Visibility Rules

* `DRAFT` products are never returned.
* `ARCHIVED` products are never returned.
* `PUBLISHED` products are returned regardless of stock status.
* Out-of-stock products remain visible in the catalog.
* Stock/purchasability is determined by variant data and is not used to hide products from this endpoint.

### Pagination Rules

* Backend page size: **20 products**.
* Server-side pagination is mandatory.
* Frontend must not request arbitrary page sizes.
* Pagination metadata is provided through `count`, `next`, and `previous`.
* Category filtering and pagination can be combined.

### Example Requests

```text
GET /api/v1/catalog/products/
```

```text
GET /api/v1/catalog/products/?page=2
```

```text
GET /api/v1/catalog/products/?category=handmade
```

```text
GET /api/v1/catalog/products/?category=handmade&page=2
```

### Pagination Rules

* Backend page size: **20 products**.
* Server-side pagination is mandatory.
* Frontend must not request arbitrary page sizes.
* Pagination metadata is provided through `count`, `next`, and `previous`.
* Category filtering and pagination can be combined.
* Page numbers start at `1`.
* If the requested page does not exist, the API returns HTTP `404` with:

```json
{
    "detail": "Invalid page."
}
```

* An invalid page does **not** return an empty `results` array.
